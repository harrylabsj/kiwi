# 方案 B 提示词（普通 WorkBuddy 任务执行云端接待部署）

> **使用条件**：当前会话没有经确认的 WorkBuddy 发布能力。历史会话工具观察不代表当前可用能力。
> **使用方法**：只在当前会话有经确认的 WorkBuddy 操作工具时继续；否则告知商家本人在安全界面操作。不得让商家把口令、密钥、token 或配对码贴回模型。平台确认弹窗由商家本人操作。
> release.json 中的 0.12.0 是已核验历史正式包的固定 pin，不代表最新版本；不要替换成未经发布核验的版本。

---

请帮我把我名下的 Kiwi 商家云端接待服务发布上线。请严格按顺序执行，每一步把真实回执（成功或报错原文）贴出来，不要伪造成功，也不要跳步。我本人处理所有凭据、配对码和必要授权；你只执行当前会话真实提供、参数已核实且我已授权的普通步骤。云端模块是否需要开通，以当前包的真实要求和平台当前工具/提示为准；信息不足时停止并询问，不猜测。任何 publishableKey、token、口令、配对码或密钥都不得进入模型可见输出、对话、日志或文件。

1. 在本任务工作区建两个不同的目录：固定发布目录 `<发布目录>`，以及放 tarball 和解包文件的 `<取包目录>`。不要把 tarball 放进发布目录。先在取包目录执行：
   ```
   npm pack @harrylabsj/kiwi-merchant-cloud@{{PACKAGE_VERSION}}
   ```
   然后解压 tarball，读取包内 build-manifest.json 的 artifact_sha256，必须等于 {{AGGREGATE_DIGEST}}；另用 `npm view @harrylabsj/kiwi-merchant-cloud@{{PACKAGE_VERSION}} dist.integrity` 取 npm 侧完整性，必须等于 {{NPM_INTEGRITY}}。任何一项不符，停下来告诉我两边的值各是什么，不要换版本、换源或重新下载试试。不要用 curl 执行脚本、不要拉源码现场构建、不要 npm install。
2. 首次发布取公网地址：确认当前账号是否已有「Kiwi商家接待」；没有可靠的只读列举能力时如实说明，不要猜。确定没有同名应用后，在固定的 `<发布目录>` 放仅用于取址的最小启动文件（index.js 与 package.json，不含商家数据或凭据）。用 当前会话真实列出的 WorkBuddy 发布能力（工具名或参数以会话实际提供的为准）**发布这个目录**一次，记录目录绝对路径、公网地址（形如 https://xxx.app.workbuddy.host）和应用标识。若已有同名应用，先核对其既有目录与地址，再决定复用方式；不创建第二个。如果发布失败或拿不到地址，先核对账号中是否已产生应用，确认没有才再次创建。出现配额不足、cloud_service_unavailable 或 useLocalImplementation:true 时停止，不做本地替代实现。
3. 准备部署目录（把 <公网链接> 换成第 2 步拿到的地址，<临时部署目录> 用 `<发布目录>` 外的**新空目录**，因为 prepare 会拒绝非空目录）：
   ```
   node package/prepare.mjs --origin <公网链接> --out <临时部署目录> --admin-bootstrap
   ```
   成功会打印 JSON 回执（部署目录、artifact_sha256、版本），核对非敏感回执摘要与随包固定值；口令不得打印到模型可见 stdout 或贴进对话；由我本人在安全终端/工作台直接查看和录入。无法隔离模型可见输出时停止。
4. 同一应用再次发布：先把第 3 步临时部署目录里的**全部部署文件**（包括首登所需的非秘密派生验证材料）复制进第 2 步的固定 `<发布目录>`，覆盖取址用的 index.js 和 package.json；不复制 tarball、口令明文、私有状态目录或取包临时文件。用 当前会话真实列出的 WorkBuddy 发布能力 从第 2 步记下的**同一目录绝对路径**再次发布，必须复用同一应用。历史实测中换目录会新建应用，即使指定旧 applicationId；当前工具无法明确保证复用时，第二次发布前停下来核对。失败就贴报错原文，不要改动部署包内容重试（尤其不要改 cloud.config.json 的 origin）；成功贴回执，并确认应用标识与公网地址均与第 2 步一致。
5. 自检（把 <公网链接> 替换后逐条执行）：
   ```
   curl -sS -o /dev/null -w '%{http_code}\n' <公网链接>/livez
   curl -sS <公网链接>/readyz
   curl -sS <公网链接>/.well-known/agent-card.json
   ```
   要求：/livez 返回 200；agent-card 的 url 字段等于公网链接。/readyz 里 identity/storage/policy 必须通过；products 一项在我导入商品并完成 Catalog 授权之前不通过属预期，不要因此说部署失败，提醒我去工作台导入商品即可。历史观察中首个请求曾出现数秒延迟，但不保证当前适用；以当前实测为准，可稍候重试，仍失败就贴响应原文，不要谎报成功。
6. 完成后告诉我公网链接与下一步：我本人在安全界面处理口令后登录 `<公网链接>/admin/login`，再打开 `<公网链接>/merchant/` 导入商品；不要再次输出口令。若工作台已提供配对入口，由我本人查看配对码并在 Catalog 授权页核对、确认「连接此服务并发布」；若没有入口或开通记录，如实报告连接流程尚未启动，不猜测授权链接，也不要宣称完整上线。

---

**技能侧补充（不复制给商家）**：商家在普通任务里完成第 6 步后，回到具有真实 Kiwi Catalog 状态查询能力的会话核对最终上线状态；只有实际回执满足 `card.published && presence=fresh` 才能宣布上线。
