# 商家接入与商品名额设计 v0.6

状态：两仓本地实现；生产数据库迁移、WorkBuddy 平台资源与真实 Buyer 询价尚未验收。本文替代 2026-09-27 的 v0.5 文档中“Listings 单独申请、管理员审批、owner token 决定发布权”的设计。v0.5 的设备接入、持钥证明、商家一次确认和名片发布仍适用。

## 商家流程

1. 商家注册 Catalog 账号并验证邮箱。注册时即分配 `merchant_id` 和 `free` 方案，默认 **20 个同时占用的 Listings 名额**；不申请发布令牌，不等待常规人工审批。
2. 商家可准备公开名片、商品和报价规则。WorkBuddy 形态还需授权平台资源；独立 Runtime 形态需在真实运行主机配置公网 HTTPS 与持久数据目录。未连接时商品保留在来源系统或草稿，不作为可询价 Listing 发布。
3. Runtime 创建接入请求并用自己的密钥证明身份。商家登录 Catalog，核对配对码和公开预览，只点击一次“连接此服务并发布”。Catalog 验证持钥证明和 HTTPS 端点挑战，建立活动绑定并发布 Agent Card。
4. 已发布 Runtime 使用活动绑定签名同步 Listings；Catalog 在每次请求检查账号状态、邮箱验证、当前绑定、已发布 enrollment、治理限制及方案额度。商家后台显示“已用／总名额”。Buyer 只有在名片和商品可发现时才能直连询价。
5. 商家主动下架释放名额；达到上限时，先下架商品或由管理员调整额度。密钥轮换、暂停、撤回和结束测试仍沿用接入运维流程。

## 三个独立的权威

| 问题 | Catalog 权威 | Runtime 所需 |
| --- | --- | --- |
| 谁是商家 | 已验证的 Catalog 账号与 `merchant_id` | 不持有账号会话 |
| 哪个实例可操作 | 活动绑定、签名公钥及已发布 enrollment | 持久保存自己的私钥，逐次签名 |
| 可公开多少条目 | `listing_plans` 与 `merchant_listing_entitlements` | 不持有额度令牌；接收额度错误并提示商家 |

owner token 既不是额度，也不是新 Runtime 的 Listings 凭据。Catalog 的旧 owner-token Listings 路径默认关闭；只有无账号存量商家在迁移期可显式开启，账号商家始终不能使用。管理员凭据保留为治理权限。以后收费只改变方案和额度的权威记录，不改变 Runtime 的签名协议，也不因支付重新接入。

## 名额口径与状态

- `product` 和 `capability` Listings 共用一个上限。`publication_state='ACTIVE'` 的行占一个名额，包括暂时 `STALE` 的行；`WITHDRAWN` 和 `SUSPENDED` 不占名额。
- 稳定商品键定位的重复同步、内容更新和幂等重试不增额。新增、从下架状态重新发布，以及恢复到 ACTIVE 前都重新检查额度。检查与写入在同一写事务中，防止并发超额。
- 降额不会立即隐藏已公开条目；若当前已用数超过新上限，允许更新现有 ACTIVE 行和撤回，拒绝新增及恢复。
- 商家主动撤回可释放名额。方案暂停时允许签名自查和撤回，拒绝发布。平台治理暂停设置 `governance_hold`，Runtime 不能通过重新发布解除；管理员先解除治理，恢复时仍受当前额度约束。
- 商品名额、请求频率限制、内容校验和治理处置分别判定。未来若要限制“每月新增次数”或计费调用量，应新增独立指标，不改变同时公开的名额定义。

## 配置、迁移与后续收费

免费方案当前默认 20，可由 Catalog 本地管理员命令调整方案上限；单个商家可以设置覆盖额度或暂停资格。所有调整写入审计。Schema 40 建立方案、商家权益、审计和治理保护；schema 41 将未经管理员自定义的旧默认 10 提升至 20，保留已有自定义额度。迁移时若现有 ACTIVE 条目超过免费上限，临时覆盖额度设为当前占用并留审计，避免突然下架。

生产数据库迁移须备份并核对既有商家、绑定及公开条目；本地测试不证明生产环境已更新。付费方案、支付回调、账期、宽限期和到期处理尚未实现。未来支付系统只能更新已审计的方案权益；不能直接签发可绕过 Catalog 检查的发布令牌。

代码与配置细节见 kiwi-catalog 仓的 `docs/listing-entitlements.md`；跨仓验收入口为 `scripts/verify-enrollment-cross-repo.mjs`。
