# 开发验证与发布候选分批

## 目的

日常功能开发不生成 `source contract`、SBOM 或发布锁定材料；这些材料只在一个明确的发布候选已稳定后一次生成。这样不改变发布门槛，只避免每个小修复都重复进入发布维护循环。

## 开发阶段

每次功能批次完成后运行：

```sh
npm run verify:development
```

这个命令覆盖代码质量、构建、测试、契约、Harness、WorkBuddy 和 Python 参考实现验证，但不会修改或重建发布来源契约、SBOM、冷安装制品或发布包。

如果它失败，继续在同一开发批次修复；不要为中间修复生成新的发布锁定或来源契约。

## 候选阶段

只在以下条件同时满足时进入候选阶段：

1. 开发批次有清晰的范围和目标版本。
2. `npm run verify:development` 已通过。
3. 不再计划把无关功能加入该候选。

然后按顺序执行：

1. 运行 `npm run release:freeze-source`，审阅生成的来源契约并提交它。
2. 在该干净提交上运行完整 `npm run verify`。
3. 按既有发布流程构建、冷安装并核验候选制品；发布前仍需现有的端到端验收与审批。

候选验证失败时，回到开发阶段完成相关修复；不要为每次失败建立新的版本号或多份并行来源契约。只有候选范围确实改变时，才重新冻结一次。

## 边界

本流程不授权发布、部署、推送或更改平台资源。它也不替代 `portfolio-release.yml`、完整发布验证、人工审批或线上验收。
