After the release owner commits the reviewed exact source, default release build-once runs:

Missing/old/drifted receipt or unknown dist refuses; no automatic rebuild or expected mutation. This receipt records a process, not a mathematical compilation proof.
2. Normal root `npm pack --pack-destination release/npm` creates this run's exact root package. New `node scripts/build-npm-shipping.mjs` cross-checks all actual root tgz payloads and every dist byte, reuses this verified dist, and performs normal standalone production stage ci/audit/SBOM without pruning original dependency/SDK files. 3. Existing synthetic cloud smoke runs against the new stage. `node scripts/build-cloud-package.mjs` builds the full cloud package using normal npm bundle plan and root controls. Normal cloud pack follows, then `node scripts/verify-cloud-package-candidate.mjs` verifies all staging bytes and actual gzip TAR/PAX payloads/SRI.
4. `node scripts/verify-npm-shipping-installed.mjs` performs new cold normal npm12 production installs of the two exact local tarballs, original CLI help and actual full-Pi/WebAuthn/committed-proof/receipt/guarded-SDK-root probes. Consumer fixtures explicitly apply the root override; this is a declared installation contract, not evidence that nested package overrides automatically govern every unrelated consumer. Runtime probes send no model input, forbid provider fetch and use only synthetic keys/new stores. Existing cloud smoke is the local synthetic HTTP startup proof, not production/platform deployment.

Project limits are plain<=256MiB (including actual expanded npm TAR budget), each normal gzip tgz<100,000,000 bytes, host-owned<=3GiB, single build<=45min from fullverify receipt start. The tgz limit is this project's conservative guard, not a verified npmjs universal hard limit. Limit or any first failure stops; do not cut SDK content or raise limits. Mac vs Linux tool binary/native installed targets are recorded accurately; do not call their tarball SRI equal without actual evidence, nor equate a dry-run bundle with a subsequent protected publish run's separately built bundle.

The default five registry jobs, protected kiwi-release human review/OIDC, immutable downloaded bundle, signing/provenance and idempotent published-version skip remain owned by the release workflow. No npm publish, dispatch, push, production upgrade, Docker, real merchant/provider/key/model charge, old DB migration or in-review platform asset operation is performed by these candidate builders. Registry success alone does not authorize deployment or WorkBuddy resubmission.

## R1 independent-control corrections

The original a668 source contract and A402 5-pass/3-fail controls remain archived. Tool admission now compares all 1942 regular files from the exact official npm12.0.2 tarball (SHA512 SRI and per-file path/size/SHA), not the entire locally cached directory. Corepack locator is optional and strictly bound to the same official hash/name/version/bin format; ordinary global npm without it passes. Unknown extras and any original payload byte change reject. The local release tool is an owned copy with only the 18 already observed generated Python cache files removed from that copy; no home/global cache is modified and no arbitrary pyc or malicious same-UID injection safety is claimed.

Actual npm TAR parsing requires aligned, complete two-zero end blocks and zero padding, validates checksums and strict newline/decimal-length PAX records, rejects duplicate/ambiguous critical bindings and duplicate payload paths. Vendor directories have no blanket state exemption. `.npmrc` is admitted only at stage root with the exact e703 credential-free 278-byte SHA; authToken/registry changes reject. The generated hidden node_modules/.package-lock.json is admitted only after stage name/version/schema, original-lock row metadata and installed-package version checks, then exact file-byte binding. Its real stageci case remains to be exercised by the frozen final build, rather than inferred from unit fixtures. No additional public vendor state-like file exception is invented without official package-tar/SRI/path/byte proof.

The fullverify receipt uses unique temporary wx creation, complete write, file fsync and normal rename for atomic visibility. Failures expose no usable final receipt and old/bad receipts are retained without rerunning; this does not prove directory-fsync power-loss durability or resistance to a hostile local writer. Current signed-confirmation memory database and guarded SDK-root close are preliminary import/proof evidence; final cold persistence requires the independent actual-file close/reopen and cloud assembly checks.
