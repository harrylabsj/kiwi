## 1 D-M0-09 M0 参数冻结

### 1.1 冻结原则

1. 下列数值是**试点上限**，不是性能测量结果，也不是法定期限。
2. 任何数值变化必须递增 `policy_version`，并记录变更人、原因、生效日和回退值；不得通过环境变量按请求临时切换。
3. 新能力限制叠加在平台、商家和 provider 配额之下，不能通过另一个 worker 或另一个用途获得额外额度。
4. 留存期限属于隐私承诺，建议在隐私/法务确认后正式生效；未确认前按更保守值执行。

### 1.3 预算关系说明

文档中“每日 20 个逻辑 run”和“每日 token 100,000/12,000”并不矛盾，但需要准入规则：

- 每个 run 准入时预留 `5,000 input / 600 output`；20 个 run 的预留合计正好是 `100,000 / 12,000`。
- 单个 run 可以超过预留，但不得超过硬上限 `24,576 / 3,072`；超出部分从当日剩余额度扣除。
- 当日额度不足以覆盖预留时，任务保持 `PENDING`，记录 `budget_exhausted`，由工作台显示原因；不得静默丢弃或把后台额度转给另一个用途。
- 前台接待预算独立保留，后台不能借用；provider 未知用量按保守值占额，重启不退款、不清零。

### 1.4 配置与变更控制

- 配置使用严格 schema，正整数/枚举校验；非法值启动失败，不静默回落。
- 时间统一 UTC 存储，界面显示 `Asia/Shanghai`；记账日期使用商家固定时区。
- 价格目录缺失时 `cost_state=unknown`，不以 token 数伪造精确费用。
- 变更流程：提案 → 记录 `policy_version`、旧值/新值、原因、生效日、回退值 → 更新配置与测试 → 发布说明。留存变更须附隐私/法务意见。

### 1.5 验证

- 单测：非法配置拒绝；日额度预留/释放/结算；20 个 run 预留不超限；超硬上限拒绝。
- 集成：前台与后台并发时前台优先；额度耗尽时 `budget_exhausted` 可见；重启后额度不清零。
- 留存：`purge_at = min(关闭 + 分类期限, 采集 + 90 天)`；后台读取不延长；备份恢复前重放删除登记。
- 证据：配置版本、`policy_version`、测试用例 ID、实际额度记录。

## 2 D-M0-10 规则入口命名

### 2.1 决议

统一使用 `automation.*` 命名空间，不新增 `jobs.proposeRule`，也不把现有 `MerchantJobs.runOnce(name)` 暴露为服务合同。

- **`automation.prepareRule`**：唯一规则候选入口，支持 `mode="template"` 和 `mode="goal"` 两种输入；返回候选、预览、假设和警告，**不启用**。
- **`automation.activate`**：唯一启用入口，消费商家确认后的 `committed_operation_ref`。
- **`automation.pause` / `automation.runOnce` / `automation.query`**：分别暂停、手动执行一次、查询状态。
- 现有 `src/merchant-runtime/jobs.ts` 的 `MerchantJobs` 仅作为定时唤醒骨架复用；新服务自己持有 `next_due_at`、occurrence 和规则版本。

**理由：**

1. 避免 `jobs.prepareRule` 与 `jobs.proposeRule` 两个入口语义重叠。
2. 避免与现有 `MerchantJobs.runOnce(name)` 的 `jobs.runOnce` 名称冲突；后者是内部调度方法，不是服务合同。
3. 保持“模型只能生成候选、商家确认后启用”的唯一路径，符合 D-M0-07 和既有审批边界。

### 2.2 输入 schema（草案）

**模板模式：**

```json
{
  "schema_version": 1,
  "command_id": "cmd_example",
  "expected_generation": 0,
  "mode": "template",
  "template": "unfinished_inquiry_digest",
  "trigger_spec": { "kind": "daily_local", "local_time": "09:00", "timezone": "Asia/Shanghai" },
  "scope": { "window": "previous_local_day" },
  "predicate_spec": { "status_in": ["NEEDS_INFO", "WAITING_APPROVAL"] },
  "action_type": "internal_summary",
  "budget": { "max_runs_per_day": 1 },
  "expires_at": "2026-12-15T00:00:00Z"
}
```

**自然语言模式：**

```json
{
  "schema_version": 1,
  "command_id": "cmd_example",
  "expected_generation": 0,
  "mode": "goal",
  "goal_text": "每天上午九点检查未推进的询价，告诉我缺什么信息并生成草稿",
  "constraints": { "output": "workbench_only", "max_runs_per_day": 1 }
}
```

**返回：**

```json
{
  "candidate_ref": "rule_candidate_example",
  "preview": {
    "when": "每天 09:00 Asia/Shanghai",
    "scope": "前一本地日的未完成询价",
    "output": "工作台报告 + 缺项草稿",
    "audience": "merchant_only",
    "max_runs_per_day": 1,
    "expires_at": "2026-12-15T00:00:00Z"
  },
  "assumptions": ["只处理已授权商品", "不发送客户消息"],
  "warnings": [],
  "content_hash": "sha256:...",
  "requires_confirmation": true
}
```

### 2.3 规则

- `mode="template"` 可确定性生成候选，不调用模型；`mode="goal"` 才调用受限模型，`goal_text` 上限 500 字符。
- 两种模式都只返回候选；模型不能提交任意 cron、收件人、客户发送或扩大数据范围。
- 仅支持 `daily_local`、`interval`、`one_shot` 三种触发；时区默认 `Asia/Shanghai`，保存 UTC。
- `action_type` 仅 `internal_summary`、`internal_draft`、`data_issue`；客户通知属于 P1 独立任务。
- 候选必须包含 `content_hash`、`base_generation`、`expires_at`；启用时 CAS 校验 `expected_generation`。
- 语义不明确、依赖未实现能力或超出权限时返回 `unsupported_capability` 或 `access_denied`，不生成“猜测版”规则。

### 2.4 错误与验收

| 场景 | 内部错误 | 对外行为 |
| --- | --- | --- |
| 模型试图直接启用/扩大收件人 | `access_denied` | 只返回候选或拒绝 |
| 触发类型/动作类型不支持 | `unsupported_capability` | 提示可选模板 |
| 并发确认/规则版本变化 | `version_conflict` | 回读当前候选，不覆盖 |
| 同命令不同业务内容 | `idempotency_conflict` | 保留原记录 |
| 额度不足 | `budget_exhausted` | 保持 PENDING，显示原因 |

**验收补充：**

- `automation.prepareRule(mode="goal")` 只返回候选；未确认前 `automation.query` 无 ACTIVE 规则。
- 商家确认后 `automation.activate` 才产生不可变 `rule_version`。
- 模型不能通过 `goal_text` 注入 cron、收件人或客户发送；越权字段拒绝。
- 现有 `MerchantJobs.runOnce(name)` 不被新服务合同调用或改名。

## 3 D-M0-01-E1 宿主主体证据请求

### 3.1 对象与截止

- **对象：** 目标买方宿主的产品与安全团队（WorkBuddy 或其他实际试点宿主）。
- **截止：** 发出后 3 个工作日回复；M0 冻结前形成结论。
- **默认：** 未回复或证据不足，按组织/代理范围记忆执行，不启用个人记忆。
- **责任人：** 产品 + 安全 + 宿主集成；证据存入 M5 证据包。

### 3.2 必须回答的问题

1. 宿主能否签发稳定、按人的 `subject_ref`？生成方式、唯一性、生命周期和撤销方式是什么？
2. `issuer` 是谁？密钥如何发现、轮换和吊销？断言使用 JWS 还是 VC？如何绑定 `audience=merchant:<id>`？
3. `assurance_class` 如何区分 `verified_person`、`verified_org`、`session_only`？同一 Agent 代理多人时如何表达 `on_behalf_of`？
4. 宿主如何证明“当前会话属于该 subject”？会话访问权与被代理主体证明是否分离？
5. 撤销后多快传播到商家？商家如何获知撤销？重放、过期、跨商家断言如何处理？
6. 是否支持负向测试：同一 Agent 两个不同 person、共享 token、安装级 UUID、撤销后重放？
7. 数据用途、留存、删除和子处理方如何约定？宿主是否允许商家保存最小主体引用？

### 3.3 必须提供的证据

- issuer 元数据与 `.well-known` 地址；
- 一份脱敏的示例断言（含 `subject_kind`、`assurance_class`、`audience`、`binding_epoch`、`proof`）；
- 密钥轮换与吊销文档；
- 撤销 API 或事件契约；
- 负向测试向量或测试环境；
- 安全联系人与事件响应时限。

### 3.4 本地验收测试

1. 签名、audience、时间窗口校验通过；篡改任一字段失败。
2. 过期、撤销、epoch 回退、跨商家断言均拒绝。
3. 同一 Agent 两个 person 不合并档案；共享 token 不生成个人档案。
4. 无断言时只走匿名接待，记忆工具返回 `access_denied`，不泄露存在性。
5. 撤销后旧游标、旧上下文和未发布结果失效。
6. 证据与测试结果写入 M5，不把宿主自述当已验证。

### 3.5 通过/不通过 gate

- **通过：** 问题 1–5 有可验证答案，证据 1–5 齐备，本地测试 1–5 通过；才可提交 D-M0-01A 升级个人记忆。
- **不通过：** 任一缺失 → 保持组织/代理范围；个人记忆列为 P1 外部依赖。
- **不得：** 用 `identityVerified=true`、共享 bearer、安装级 UUID、昵称/电话/IP 代替主体断言。

### 3.6 请求邮件模板

> 主题：请确认买方宿主的主体断言能力（Kiwi 商家智能体试点）
>
> 我们需要在 M0 冻结前确认贵方宿主能否提供按人的、可验证、可撤销的主体断言，用于客户跨会话记忆的授权边界。请协助确认：
>

> 2. issuer、密钥发现/轮换、JWS/VC 与 audience 绑定；
> 3. `assurance_class` 与同一 Agent 代理多人时的 `on_behalf_of`；
> 4. 会话归属证明与撤销传播时限；
> 5. 可提供的示例断言、撤销契约和负向测试环境。

> 若当前只能提供安装级或 token 级标识，我们将在本期按组织/代理范围设计，不建立个人档案。请在 3 个工作日内回复；未回复将按该默认路径执行。
